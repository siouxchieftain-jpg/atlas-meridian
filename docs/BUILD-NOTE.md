# Build note

ATLAS v3.5.1 is a research prototype for referrals from GPs (fastleger) to specialist mental health services (DPS) in Norway, built for a formative evaluation. All patients, clinicians and figures in it are fictional. This note says what was built and how. [PLAN.md](PLAN.md) lists the screens, the steps and the forms; [MERIDIAN-1.1.md](MERIDIAN-1.1.md) gives the design rules the build added to Meridian.

## What the site holds

- **The app** at the site's address. Study mode opens there. Review mode has its own address, which goes to reviewers directly; study mode never links to it.
- **`sendt.html`**, the page Nettskjema's receipt button leads to when a form was answered in a new tab. It records in the browser that the step was sent and leads back to the study, where the participant was (its link carries `?kvittering`, so it does not ask «Ikke deg?»). A receipt that names its form (`sendt.html?skjema=S3`) marks only that step; the feedback form's receipt (`?skjema=S9`) marks none and offers to close its tab, with no link back into ATLAS (a second ATLAS in that tab could open a case form twice). The form script writes the name into every receipt and `verify` checks it; a receipt without the name marks the step that is waiting, as in v3.
- **`informasjonsskriv.html`**, the information letter, in Norwegian and English (the language ATLAS is set to opens first), with a PDF of each language (`informasjonsskriv.pdf`, `information-letter.pdf`) printed from the page by `npm run letter`. The script drives an installed browser over the DevTools protocol, with nothing to install; the published PDFs are printed with Microsoft Edge on Windows, so they carry Segoe UI, and they are tagged, with an outline and «Side x av y» on every page. Velkommen links to the letter, and S1's consent («Jeg har lest informasjonsskrivet og vil delta») refers to it.
- **`meridian/`**, the Meridian design language as exported from the design tool, linked from review mode only. On the site its two React files are served from the site itself and checked against the integrity hashes the export pins (`app/scripts/assemble-site.mjs`); the copy in the repository is unchanged.

## Stack

- React 19.2.8, TypeScript 5.9.3 in strict mode, Vite 7.3.7 with a relative base, so the site works under any path.
- Fluent UI React v9: `@fluentui/react-components` 9.74.9 and `@fluentui/react-icons` 2.0.344, pinned exactly. Styles are Griffel `makeStyles` with Fluent tokens; the Meridian values that have no Fluent token (the band, the dawn and a few sizes) live in one module, `app/src/theme/constants.ts`.
- A small hash router of the project's own. No CSS framework, no other UI library, no runtime CDN, no analytics, and no fonts or scripts from third parties.
- Vitest 4.1.11 for unit tests; Playwright 1.56.0 with axe-core for end-to-end tests on the built site.

## Content

- Every text the app shows is in `app/src/content/`, in Norwegian (`nb`) and English (`en`): the interface strings (`strings.json`), the cases (`cases/*.json` and `v5.json`), the tours, the ordliste, the design notes and the instrument (`instrument.json`: each item's wording, scale and codebook name). A vignette sentence, an English string or an item's wording changes in one file.
- `sources.json` lists the 303 texts reused from the earlier ATLAS prototype and the project's own documents, with where each came from and any declared substitution (for example a changed fictional name). The content check confirms that each still reproduces the text the app shows.
- Every clinical fact written new for v3 is listed for a clinician's check in [CLINICIAN-CHECK.md](CLINICIAN-CHECK.md).
- `app/public/atlas-config.json` holds the Nettskjema addresses, the information letter's address and the contact lines. The app reads it at run time.
- `app/scripts/nettskjema.mjs` makes the 14 Nettskjema forms from `instrument.json` through the Nettskjema API (`plan`, `create`, `update`, `verify`, `status`), writes their addresses into `atlas-config.json` and reads each form back to check it against the instrument. With `--round pilot` it works on the pilot set instead: a copy of the twelve study forms, titled «(pilot)», whose addresses go under `pilotForms`. `open --until YYYY-MM-DD` and `close` set a set's open period (opening the study set also needs `--study`), and `status` shows answers and whether each form is open. The API client's ID and secret, and the editor's Nettskjema username, stay in a file outside the repo. The forms are made closed; `open` gives a set its open period (or the owner does it in Nettskjema).

## Study mode and the forms

- Each study step opens one Nettskjema form, without login, in a panel beside the case where the window is wide enough (an embedded form, `embed=1`), over the case where it is not, or in a new tab. ATLAS fills and locks the context fields through the form's address (`CB<codebook>=<value>&LCK<codebook>=true`), with every value encoded by `encodeURIComponent`. No name or free text is ever sent as a locked field. The one code is the study name (`studienavn`, for example «Rolig elg 27»): random, made in the browser when the role is chosen, kept only in that browser, and sent locked in every study form so one person's forms can be sorted together. Nobody holds a key to who has which name.
- From an embedded form, ATLAS acts only on messages from `https://nettskjema.no`: the form's height, `scrollToStart`, `submitFinished` and `submitFailed`. A form answered in a new tab returns through `sendt.html`; where the browser keeps no storage, the participant confirms with «Jeg har sendt skjemaet».
- A step whose form address is empty shows «Dette skjemaet er ikke klart ennå.», offers no skip and cannot be passed.
- Preview forms are built from `instrument.json`, so they ask what the Nettskjema forms ask. They keep answers in the browser, say so on screen and export CSV. In study mode they run only when the address carries the preview flag, which no participant link carries; in review mode the feedback forms (R1, R2) are the Nettskjema forms once they have addresses, and preview forms before that.
- The end-to-end checks never reach Nettskjema: they answer a stand-in form, or run with no form addresses.
- In study mode the browser's storage holds progress, settings, the role, the «Om deg» answer and the study name; these leave the browser only as locked form fields. Nothing else is collected.
- The locked field `versjon` carries the package version and the short commit the workflow built (for example `3.2.0-66ca8de`), so each answer can be traced to the build that collected it.
- **The pilot round.** `atlas-config.json` names the round. With `"round": "pilot"`, the study forms come from `pilotForms`, the `versjon` of every study form ends in `-pilot` (R1 and R2 keep theirs), the header shows a «Pilot» chip and Velkommen says the answers are kept out of the study's data. Setting `"round": "study"` ends the pilot without a code change. A pilot form without an address is «ikke klart ennå», never the study form.
- **The study period.** `studyPeriod` holds the first and last day. In the study round, after the last day (by the date in Norway), every address shows Velkommen saying the study has ended, and nothing starts; the pilot round never closes.
- **Feedback along the way (S9).** After S1, a «Gi tilbakemelding» tab in brand, docked to the right edge (board 8b), on every study page asks which part of the screen the feedback is about and opens S9 with the role, the study name, the screen (`side`), the part (`seksjon`) and the build locked; S9 has no `steg`. The study asks for it at two moments only, the end of the tour and the end of each case (after its form is sent), once each. S9 never replaces a step form that is open, so the answers in it are never lost: then it opens in a new tab.
- **Welcome back.** The study link opened again in a browser that holds a session (a role chosen) shows Velkommen's welcome back first: where the participant is, the study name, «Fortsett der du slapp» and «Ikke deg? Start som ny deltaker», which removes this browser's study session (what was sent stays in Nettskjema). Once S1 is sent, Velkommen always shows it. A reload or an address inside the study keeps its place.

## The guide's reader

Informasjonsguiden and the margin «Hva DPS ser etter» read the referral text as it is written, section by section, for the five criteria a GP can document. The reader is a set of Norwegian and English word patterns in `app/src/engine/criteria.ts`. It runs in the browser, sends nothing anywhere and has no model behind it. It says «Omtalt» or «Ikke funnet ennå», never that something is missing or that what is written is enough, and it never blocks sending.

Its tests include phrase sets that agents wrote without seeing the reader. Each set was measured once, then added as a test that bounds the reader's error count on that set, so a later change cannot make it worse unnoticed.

The Pages workflow runs all of them on every push to `main` and deploys only when every step passes. It also fails when the generated documents are out of date. A pull request to `main` runs the same checks and publishes nothing.

Before its release v3 went through eleven review rounds by reviewers who had not built it, each round covering function and accessibility; the last round found nothing critical or important. v3.1 had two reviews by reviewers who had not built it: a review of the branch, whose 13 findings were fixed, and a release review, which found no blocker; its smaller points were fixed before the merge. v3.2 had two more: a build review (one blocker, the overview squeezed beside an open form, and twelve smaller findings) and a design review against Fluent 2 and Microsoft 365 (two must-fix and eleven should-fix findings). All were fixed, or recorded with a reason, before the release. v3.3 had a review by a reviewer who had not built it, against the approved boards and the live 3.2: no blocker, nine should-fix and five nice-to-have findings. They were fixed, with these parts left out on purpose: the overview's five-item rail, its counts drawn as chips, a clock line and «Hele timelisten» (the study's overview has no other pages to go to, and a frozen clock would contradict the cases as they are done), and radio circles on the choice cards (G-20 marks the choice with an outline and tint). v3.4 had three independent reviews of the start page and the list before it was built: design and interface logic, study flow and integrity, and accessibility. Their blockers were fixed: one door per destination and a defined way back from a case; nothing before a case that hints at its outcome (3.3 named DPS's reply to Astrid «Retur med råd» on the overview, before the case shows the letter without ATLAS); the artwork kept clear of text at every width and zoom. A review of the build against those decisions found no blocker; its five should-fix points were fixed. Their smaller points were fixed too, with two parts kept on purpose: the start page's own study-name mark beside the header's (it helps the participant remember the name the forms ask for), and «Timeliste i dag», the approved board's word, over «timebok». The review records are kept with the project's private records. v3.4.1 answers Chieftain's check on a large office monitor: every page kept to a 1,600 px column on the left of the window, with an empty band on the right; «Frister» crowded its dates when it got a quarter of a row; and Velkommen's card left its content in the middle with empty bands above and below. Velkommen's five steps sit at the foot of its card, and the information letter is a button in its top right corner. v3.5 answers Chieftain's request to follow board 12a: on a big screen the start page left most of the window empty, because the 3.4 reviews had taken out 12a's key figures, the day's tasks, «Kommende», the GP's deadline strip and the rest of the day. ## Size

No script chunk is above 400 kB gzipped. At 3.3.0 the app's own code is about 186 kB gzipped and the libraries (React and Fluent) a chunk of their own of about 226 kB, which a new build of the app leaves cached; review mode loads as its own chunk of about 12 kB.

## Known limits

- Light theme only (forced colours are supported).
- Pages take the height their content needs and scroll down; nothing scrolls sideways at any width from 320 px (checked on every study and review screen). 3.2 dropped v3.1's «one screen tall», which made the study's own pages dense.
- Two registers (Meridian): the study around the work is a guide surface with the dawn, the artwork and one sheen start action (Velkommen, the study name on Om deg, the start page's greeting and the list's study card, the card before the tour, the tour, the briefing's task, help, the end of a case and Takk); since 3.4 each role's surfaces wear their own artwork, the coral-led wave for the GP and the lavender-led wave for DPS, and Velkommen, where the role is chosen, the organza (G-35); the work itself sits on Meridian's white panels with one solid primary action (3.3 put back what 3.2 had narrowed to Velkommen and the tour). Every page of a case carries the same case header, and notices are Fluent message bars under it.
- A page shorter than the window reaches down to the footer (its panel, or a case's last card, grows); a longer one scrolls down (3.3). The start page's parts sit on the frame wash, each as tall as its content. A help dialog keeps its header and «Lukk» in view; on a short window only its body scrolls.
- Not built, by decision: voice notes, replacing the information guide's count («4 av 5 kriterier omtalt») with the GP's own sentences, a redesign of the case views, and a suite bar that shows ATLAS as one app in a larger journal system (mocked on the design canvas and parked).
- Every target is at least 24 × 24 px; the study recommends a laptop, and touch sizes are not set.
- 2B-4 in the specification (patient trajectory input) is not built: no case reaches a treatment checkpoint ([TRACEABILITY.md](TRACEABILITY.md)).
- Two Nettskjema behaviours are checked in the pilot: whether a page with text only is allowed (the stop page of the case forms) and whether the receipt page keeps the button back to ATLAS.
